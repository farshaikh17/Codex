# Quality benchmark (backlog H)

A small, hand-labelled fixture set and a scorer that any assessor can be measured against: the gates in ENGINE steps 3+4, the review queue in step 5, or a manual process. Standard library only, and no network (it passes under farshaikh17/Codex#1's socket-blocking offline CI).

```
python -m bench validate      # are the labels internally consistent?
python -m bench collection    # run the collection scenarios through collect.collect()
python -m bench baselines     # trivial assessors, to show the metrics discriminate
python -m bench engine        # score engine/extract.py when it is present (PR #2)
python -m bench score PREDICTIONS.json
```

## Files

| File | Content |
|---|---|
| `bench/fixtures/candidates.json` | Two synthetic candidates (`cand-in`, `cand-us`): residence, work authorization, accepted engagement, salary floors per currency (base, per year), years of experience, job families, prior applications. Not real people. |
| `bench/fixtures/cases.json` | 17 synthetic postings plus 2 permitted public excerpts. Each has expected evidence states and, per candidate, expected relevance, the five gates and a decision. |
| `bench/fixtures/collection.json` | 6 multi-step feed scenarios with exact expected collector outputs, downstream labels (duplicate groups, relisting, salary-only recheck), and 1 queue-interruption scenario. |

## How the labels are made

- **`author_constructed`** (synthetic): the posting text is written so that it states the fact the label asserts. Every `pass`/`fail` gate label carries a `basis` that `validate()` checks is quoted verbatim from the posting. `unknown` labels carry a reason instead. Synthetic postings use `example.invalid` URLs and invented roles.
- **`needs_human_review`** (real excerpts from the official GitLab and Zapier feeds, captured 2026-10-26): labelled by the author, but excluded from every gating metric until a person confirms them. They carry partial gate labels only, and no decision.
- Labels are never generated by running an assessor. When an assessor disagrees with a label, a person decides which one is wrong. Changing a label to match an implementation needs a reason in the commit.

## Decision rule and vocabularies

- Gates (the same names as ENGINE step 4): `geography`, `engagement`, `experience`, `salary`, `prior_application`. Each one is `pass`, `fail` or `unknown`.
- Decision: any gate `fail` → `EXCLUDE`; every gate `pass` → `READY`; otherwise `NEEDS_REVIEW`. `validate()` rejects labels that break this rule.
- Relevance (`match` / `no_match`) only orders review. It never changes a decision.
- Evidence states (the same as ENGINE step 2): `stated`, `not_stated`, `conflicting`, `not_retrieved`. Availability: `listed`, `missing`, `closed_stated`.
- Compensation `basis`: `base`, `ote`, `variable_only`, `unspecified`. A fixed amount with no variable component mentioned counts as base when compared with a floor. Ranges are never converted between currencies or periods. An hourly rate against an annual floor is `unknown`.
- Conflicting geography (for example "Remote - Worldwide" plus "only hire in the US and Canada") is labelled `unknown`, not `fail`. Unsupported READY is penalised first, and auto-excluding on conflicting evidence would hide false exclusions.

## Metrics

| Metric | Meaning |
|---|---|
| `false_ready` | Predicted READY where the label isn't READY. **Primary metric; `score` exits 1 if it is non-zero.** |
| `incorrect_exclusions` | Predicted EXCLUDE where the label is READY or NEEDS_REVIEW. Reported alongside false READY, so caution can't hide behind exclusions. |
| `missed_ready` | Labelled READY but not predicted READY. |
| `retained_unknowns` / `expected_unknowns` | NEEDS_REVIEW labels kept as NEEDS_REVIEW. |
| `gate_agreement` | Per gate, for predictions that include gates. |
| `missing` | Labelled pairs with no prediction. Listed, never silently skipped. |
| Extraction | Evidence-state agreement per field, expected warnings found, compensation detail agreement (`currency`, `period`, `basis`, `estimated`, `variable_mentioned`, `equity_mentioned`, `multiple_ranges`). |
| Duplicates | Pairwise precision and recall against the labelled duplicate groups. |
| Queue | All items completed, each exactly once, correct pending set after interruption. |

Baselines on the 30 labelled decisions (5 READY, 10 NEEDS_REVIEW, 15 EXCLUDE):
- **Always-READY:** 25 false READYs.
- **Always-exclude:** 15 incorrect exclusions.
- **Always-review:** 0 false READYs and 0 incorrect exclusions, but all 5 READYs missed.

## Prediction format

```json
{"assessments": [{"case": "remote-us-only", "candidate": "cand-us", "decision": "READY",
                  "gates": {"geography": "pass", "engagement": "pass", "experience": "pass", "salary": "pass", "prior_application": "pass"}}],
 "extraction":  [{"case": "missing-salary", "fields": {"compensation": "not_stated"}, "warnings": [], "compensation": {}}],
 "duplicate_groups": [["lever:bench-a:a1", "lever:bench-b:b1"]],
 "queue_runs":  [{"scenario": "interrupted-batch", "processed": ["q1", "q2", "q3", "q4", "q5"], "pending_after_interrupt": ["q3", "q4", "q5"]}]}
```
