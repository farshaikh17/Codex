# Quality benchmark (backlog H)

A small, hand-labelled fixture set and a scorer that any assessor can be measured against: the gates in ENGINE steps 3+4, the review queue in step 5, or a manual process. PR #2 ships its own gate cases (`python -m engine.benchmark`, written by that session). This set is written independently, so each catches what the other's author didn't think of. Both use the same vocabulary. Standard library only, and no network (it passes under farshaikh17/Codex#1's socket-blocking offline CI).

```
python -m bench validate      # are the labels internally consistent?
python -m bench collection    # run the collection scenarios through collect.collect()
python -m bench baselines     # trivial assessors, to show the metrics discriminate
python -m bench engine        # score engine/extract.py when it is present (PR #2)
python -m bench score PREDICTIONS.json
```

## Files

| File | Content |
|---|---|
| `bench/fixtures/candidates.json` | Two synthetic candidates (`cand-in`, `cand-us`): residence, work authorization, accepted engagement, salary floors per currency (base, per year), years of experience, job families, prior applications. Not real people. |
| `bench/fixtures/cases.json` | 19 synthetic postings plus 2 permitted public excerpts. Each has expected evidence states and, per candidate, expected relevance, the five gates and a verdict. |
| `bench/fixtures/collection.json` | 6 multi-step feed scenarios with exact expected collector outputs, downstream labels (duplicate groups, relisting, salary-only recheck), and 1 queue-interruption scenario. |

## How the labels are made

- **`author_constructed`** (synthetic): the posting text is written so that it states the fact the label asserts. Every `pass`/`fail` gate label carries a `basis` that `validate()` checks is quoted verbatim from the posting. `unknown` labels carry a reason instead. Synthetic postings use `example.invalid` URLs and invented roles.
- **`needs_human_review`** (real excerpts from the official GitLab and Zapier feeds, captured 2026-10-26): labelled by the author, but excluded from every gating metric until a person confirms them. They carry partial gate labels only, and no verdict.
- Labels are never generated by running an assessor. When an assessor disagrees with a label, a person decides which one is wrong. Changing a label to match an implementation needs a reason in the commit.

## Decision rule and vocabularies

- Gates (the names PR #2 shipped at 8794ca8): `geography`, `engagement`, `qualifications`, `salary`, `application_history`. Each one is `pass`, `fail` or `unknown`.
- Verdict: any gate `fail` → `excluded`; every gate `pass` → `ready`; otherwise `conditional`. `validate()` rejects labels that break this rule. It also rejects a `qualifications` label of the form "N+ years of X experience" that contradicts the candidate's years of X on file.
- Relevance (`match` / `no_match`) only orders review. It never changes a verdict.
- Evidence states (the same as ENGINE step 2): `stated`, `not_stated`, `conflicting`, `not_retrieved`. Availability: `listed`, `missing`, `closed_stated`.
- Compensation `basis`: `base`, `ote`, `variable_only`, `unspecified`. A fixed amount with no variable component mentioned counts as base when compared with a floor. Ranges are never converted between currencies or periods. **Owner rule (2026-10-26): a bare "$" means USD only when every listed location is in the United States.** Otherwise the currency is not established and salary is `unknown`. `validate()` enforces this on labels. **Owner rule (2026-10-26): pay stated as commission-only, with no base salary, fails a base salary floor.** It is a stated fact, not missing evidence. This differs from OTE-only pay, where the base isn't stated, so salary is `unknown`. **Owner rule (2026-10-26): a candidate may have salary floors in several currencies.** A stated range is compared only with the floor in its own currency, never converted. With no floor in that currency, salary is `unknown`. A range limited to residents of another country (for example GitLab's "for residents of the United States only") doesn't apply to a candidate outside that country. `cand-in` (INR 3,000,000 and USD 60,000) exercises this. `bench/engine_adapter.py` still passes PR #2 only the INR floor until its config accepts several. An hourly rate against an annual floor is `unknown`.
- Conflicting geography (for example "Remote - Worldwide" plus "only hire in the US and Canada") is labelled `unknown`, not `fail`. Unsupported READY is penalised first, and auto-excluding on conflicting evidence would hide false exclusions.

## Metrics

| Metric | Meaning |
|---|---|
| `false_ready` | Predicted `ready` where the label isn't `ready`. **Primary metric; `score` exits 1 if it is non-zero.** |
| `incorrect_exclusions` | Predicted `excluded` where the label is `ready` or `conditional`. Reported alongside false READY, so caution can't hide behind exclusions. |
| `missed_ready` / `missed_exclusions` | Labelled `ready` / `excluded`, but predicted something else. |
| `retained_unknowns` / `expected_unknowns` | `conditional` labels kept `conditional`. |
| `gate_agreement` | Per gate, for predictions that include gates. |
| `missing` | Labelled pairs with no prediction. Listed, never silently skipped. |
| Extraction | Evidence-state agreement per field, expected warnings found, compensation detail agreement (`currency`, `period`, `basis`, `estimated`, `variable_mentioned`, `equity_mentioned`, `multiple_ranges`). |
| Duplicates | Pairwise precision and recall against the labelled duplicate groups. |
| Queue | All items completed, each exactly once, correct pending set after interruption. |

Baselines on the 34 labelled verdicts (6 ready, 11 conditional, 17 excluded):
- **Always-READY:** 28 false READYs.
- **Always-exclude:** 17 incorrect exclusions.
- **Always-review:** 0 false READYs and 0 incorrect exclusions, but all 6 READYs missed.
