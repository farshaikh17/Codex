# Incident 2026-11-05: D1 free-tier daily read limit

## What happened

From before 17:44 UTC every dashboard route that queries D1 answered 500 (and `/api/sources` crashed with Cloudflare
error 1101). `/api/version`, which does not use D1, kept answering 200.

## Confirmed root cause

The diagnose run [42094338012](https://github.com/farshaikh17/Codex/actions/runs/42094338012) (`mode = diagnose`,
read-only) captured the Worker's own log line for `/api/health`:

```
D1_ERROR: Your account has exceeded D1's free tier daily row read limit. Upgrade to a paid plan or wait until tomorrow
(midnight UTC) to continue.
```

`wrangler d1 info` in the same run: `rows_read_24h` 11,506,856 (free limit 5,000,000 per UTC day), `read_queries_24h`
3,667, `rows_written_24h` 7,847, database 22.2 MB. `SELECT 1` (0 rows read) still succeeded.

Few queries, each reading thousands of rows. Measured locally on Cloudflare's local D1 engine with production-sized
synthetic data (2,123 jobs, 4,246 qualifications, 4,246 scores, 12 applications, 44 history rows):

| Request | Rows read before | After the query fix | Cached |
|---|---:|---:|---:|
| `GET /api/jobs` (Farhan, 25 rows) | 90,402 | 19,985 | 1 |
| `GET /api/analytics` (per candidate) | ~17,980 | ~17,980 | 1 |
| `GET /api/dashboard/overview` | 16,508 | 16,508 | 1 |
| `GET /api/automation/status` | 7,155 | 1,333 | 1 |
| One pass over every public route (both candidates) | 270,402 | 188,251 | 103 |
| Worker cron tick (idle, daily budget used) | 3 | 3 | - |
| Collector sync run 42066372766 (from its log) | 245 | - | - |

What multiplied the reads:

* The "latest application" join (`rowid IN (SELECT MAX(rowid) ... GROUP BY candidate_id, job_id)`) was re-evaluated for
  every qualification row: about 30,000 rows to count 2,123.
* The Automation view refreshed `/api/automation/status` every 15 seconds while open (~1.7 M rows an hour).
* Every tab switch reloaded all six datasets; every keystroke in search re-ran the job query.
* Release-day verification traffic: smoke tests (~22 routes each), real-browser suites on two viewports, and manual
  probes, each pass costing ~270,000 rows.

Not the cause: the Worker cron (3 rows per idle tick, about 2,200 a day) and the GitHub collector sync (245 rows read,
0 written for one run). Neither duplicates the other: the cron discovers postings from its own source list in small work
units; the sync imports the collector's snapshot files.

## Repair (commit on branch `builderbranches-d1-incident`, see the PR)

* Query: the latest-application join is a `MAX(rowid)` lookup on the `(candidate_id, job_id)` index (same rows).
* Read cache (migration 0009): public answers 30 minutes, operator answers 10 minutes, keyed by deployed commit, access
  level, path and sorted query; cleared by any successful operator change. Collector and cron changes appear when an
  entry expires.
* Read meter (migration 0009): each cache miss adds D1's `meta.rows_read`; after 2,500,000 public rows in a UTC day,
  visitors get the last cached answer or a 503 until midnight UTC. Operator reads are counted, never blocked.
* Index for the latest successful discovery run.
* Frontend: no reload on tab switch, search debounced (400 ms), Automation refresh every 2 minutes and only while visible.
* Failures: database availability errors answer 503 with `Retry-After`; the cause is logged with the path only. No
  request ends in an uncaught exception.
* Release checks: every API answer carries `X-Worker-Commit`; the smoke test waits for the expected commit and judges
  only answers that commit produced.

## The two private-field smoke failures in release run 42063986532

At 16:25:29-30 UTC, 1-2 seconds after the deploy, the first `/api/jobs` answer contained the key `manual_override_reason`
and the first `/api/applications` answer contained `notes`. Every later check passed, including the verify run 42066342092.

What is established: the released Worker removes those keys from every public answer at any depth (`stripPrivate`,
covered by `public viewing: every public read ... holds no private field`), and the previous Worker served those fields
to everyone. What is not established: which version answered those two requests. The release smoke test checked the
version once, before the first data request, so it could not tell. The test now refuses to judge any answer whose
`X-Worker-Commit` is not the released commit, so a recurrence will be identified rather than inferred.

## Review rounds before release (taken over by the coordinating session)

Two independent reviews of the repair found and fixed, with tests that fail on the previous code:

* Uncacheable public reads (an odd `search`, `limit=500`, the India Remote list) were not budgeted or metered, so a visitor could
  still spend the free read allowance outside the meter. Every public read route is now budgeted and metered, cached or not; the
  cache switch (`RESPONSE_CACHE=off`) no longer disables the budget.
* Cache keys used the raw URL path, so percent-encoded aliases of one job minted unlimited entries, and a pattern-based exemption
  let them bypass the daily write cap. Keys now use the decoded canonical path, candidate ids in paths are validated, and the cap
  applies to everything except a fixed set of dashboard page loads. Search entries get a tenth of the write allowance.
* Caching depended on the deploy-time `GIT_COMMIT` variable, so a plain `wrangler deploy` would have silently switched it off. The
  namespace is now a code constant plus the commit when present, and every release flushes the cache.
* A failed cache invalidation now refuses the operator change (one retry first); an old answer is never served as "stale" across an
  operator change.
* The login-attempt limiter wrote a row on every request that carried a wrong key, so one address repeating one wrong key could spend
  the free write allowance (100,000 rows a day). The identical wrong key inside the window now writes nothing.

Known trade-offs (documented, not fixed): one global cache generation means every operator change expires every cached page for both
candidates, so many operator edits in one day cost reads and can bring the daily public budget forward; cron and collector reads are
not in the meter (about 3 rows per idle cron tick and about 245 rows per collector run); a plain `wrangler deploy` that changes
response shaping without bumping `CACHE_SCHEMA` would serve old bodies until entries expire.


## Resolution record (2026-11-06)

The release after the 00:00 UTC reset is recorded in `QA_REPORT.md`. The Worker serving `efdcb7c` answers every public data route with 200 and `X-Cache: HIT` on repeats, `/api/version` reports the deployed commit, anonymous writes return 401, and protected records are unchanged. Measured D1 reads for the first 25 minutes of the new day were 0.64M rows (almost all release and verification traffic). Full-day usage with ordinary traffic has not been measured; the cache and the 2.5M-row public read meter bound the exposure.
